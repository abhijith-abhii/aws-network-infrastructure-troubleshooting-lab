# Operations, drift, state, and teardown

## Normal workflow

Use one repository copy and one Terraform default workspace per lab. Run commands from the repository root. The controller always passes an absolute `.lab/config.tfvars.json`, captures Terraform's output inventory, and restricts SSM commands to the two recorded IDs after checking tags/account. It never deletes by account-wide discovery. The one tag-scoped volume listing in removal verification is read-only.

```bash
python3 scripts/lab.py deploy --approve
python3 scripts/lab.py test
python3 scripts/lab.py inject nacl --approve
python3 scripts/lab.py evidence
python3 scripts/lab.py restore --approve
python3 scripts/lab.py test
```

The current scenario is stored both in Terraform output and the local input file. Fault injection refuses a second fault while either indicates a non-baseline state. It runs baseline tests first, then allows only the selected fault's resource address in the plan. It rejects unrelated resource drift and replacement. Restoration permits changes only at the five documented fault resource addresses, and verifies the baseline afterward. A partially applied fault can be restored because the intended input was saved before the apply.

Do not edit AWS routes/SGs/ACLs manually during the controlled exercises. If you intentionally change infrastructure for your own experiments, inspect/reconcile it with Terraform before returning to the scenario workflow:

```bash
terraform -chdir=terraform plan -var-file=../.lab/config.tfvars.json
```

A failed safety check is a reason to review the plan, not to delete state or bypass the guard. Update code or revert the accidental edit; use a separately reviewed direct Terraform apply only for an intentional design change. `deploy` rejects deletions/replacements. Fault scenarios change a route, SG rule, ACL rule, DNS record or endpoint policy, never an EC2 instance.

## Dependency lock and AMI reproducibility

`terraform/.terraform.lock.hcl` is generated by Terraform and committed. Do not fabricate hashes or ignore it. CI uses `init -lockfile=readonly`. After an intentional provider upgrade:

```bash
terraform -chdir=terraform init -upgrade
terraform -chdir=terraform providers lock -platform=linux_amd64 -platform=darwin_arm64
./scripts/static-checks.sh
# Review and commit the changed lock file and validation evidence.
```

Root constraints allow compatible 6.x AWS provider versions; the lock selects an exact version. Terraform CLI is pinned separately in CI. The AMI is pinned by scripted deploy in the ignored local file. Record it with `inventory`. Direct Terraform use without `ami_id` resolves the latest public parameter and can propose image replacement on a later plan; always pin when reproducing a lab. Never update packages/image in the middle of a scenario.

## Recover interrupted operations

- An interrupted apply may leave resources running. Keep Terraform state and `.lab/` intact. Re-run `deploy --approve` after a partial first deployment, or `restore --approve` after a partial fault.
- Terraform state locking is enabled. Confirm no other Terraform process is running before any lock recovery; never blindly force-unlock an active apply.
- A failed SSM command is not proof of network fault. Confirm instance online status and inspect bootstrap logs. Restoration calls the AWS control plane from your workstation before attempting SSM verification.
- If accidental changes also broke management, `restore` rejects unrelated drift. Review the direct Terraform baseline plan and reconcile the extra changes; do not open port 22 as a shortcut.
- Renew expired SSO sessions with `aws sso login --profile netlab` and repeat the failed step under the same account.

## Teardown and independent checks

```bash
python3 scripts/lab.py evidence
python3 scripts/lab.py destroy --approve
python3 scripts/lab.py verify-destroy
terraform -chdir=terraform state list       # expected: empty, after successful removal
```

`destroy` snapshots the last full inventory locally, plans `-destroy`, and deletes only state-managed resources. Terraform removes the tracked object, then the bucket, instances/disks, endpoints, peering, DNS zone, Flow Logs/group, IAM profiles/roles and VPC networking. The subsequent bounded check tests instance termination, VPC/endpoint/role/profile/bucket/zone/log/volume removal and empty state. Authorization failures are errors, never interpreted as deletion. EC2 may still describe terminated instances; this is accepted as terminated, not running.

The verifier waits up to ten minutes for asynchronous removal visibility. If a first deployment failed before complete outputs existed, Terraform can still destroy its partial state, but inventory-based verification cannot certify the absent snapshot. The script reports that limitation. Inspect all resource entries from `terraform state list` before destruction and the lab's tagged VPC/EC2/endpoint/volume/log/IAM/DNS resources afterward. Do not claim a clean AWS deletion based only on an empty local state file.

The test bucket has `force_destroy=false`. If an untracked object blocks deletion, list **only this bucket**, inspect its keys/versions and explicitly remove or archive your additions; rerun destroy. There is no `aws s3 rb --force` cleanup shortcut. A private zone with extra unmanaged records may similarly require deliberate cleanup.

After successful verification, inspect Billing/Cost Explorer after reporting catches up. Historical SSM command records and billing history can remain after resources are removed. Local evidence/state backups are not cloud resources; secure or remove them according to your own needs. Stopping EC2 alone is not teardown.

## Optional S3 remote state

Start with local state to avoid a circular bootstrap. For collaboration, create a **separate** private, encrypted, versioned state bucket through an administrator or separate bootstrap project. Do not use the disposable test bucket. Restrict state/key and lock-file permissions to the deployer role. Modern Terraform S3 backend supports native locking via `use_lockfile=true`; DynamoDB-based locking is deprecated. [HashiCorp S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3).

Create ignored `terraform/backend.tf`:

```hcl
terraform {
  backend "s3" {}
}
```

Create an ignored `state.backend.hcl` in the repository root, replacing placeholders:

```hcl
bucket       = "YOUR-EXISTING-PRIVATE-STATE-BUCKET"
key          = "personal-labs/aws-netlab/terraform.tfstate"
region       = "us-east-1"
encrypt      = true
use_lockfile = true
```

Then `terraform -chdir=terraform init -migrate-state -backend-config=../state.backend.hcl`. Verify the migrated state and test the lock before deleting a local backup. Backend authentication uses the same SSO environment, never credentials in the file. S3 ListBucket/GetObject/PutObject on the state key and Get/Put/Delete on the `.tflock` key are needed; version recovery/KMS may need additional rights. This backend is intentionally outside lab teardown and has its own storage cost and cleanup lifecycle. Do not enable it in credential-free CI.
